## 1. ✅ 缺口 A：按键 / 键位注入通道 —— **mod 侧已解决（`taclight@0fde59a`）**，harness 侧只差"怎么用 / 怎么验收"

**状态（2026-09-27 更新）**：由 `taclight` 仓 `0fde59a`（`channel/KeyInject.java` + `KeyInjectContract`，84 checks）关闭。
**本仓（harness）里没有这部分代码** —— 实现、守卫、收据都在 mod 侧；本节只负责写清**用法**与**可判定验收**，
免得每一轮的人重新猜（这正是"harness 专属开发"要消掉的摩擦）。

<details>
<summary>背景：当初为什么立项（保留原文，不抹）</summary>

- 真机三张截图**全黑**：无光斑、无光锥、**目标格在画面里无法指认**。
- 直接原因：截图上模组自己的提示写着 **`[TacLight] ✓ 配套包已激活: L=手电筒开关, K=霓虹调试`**。
- `input.set` 只能驱动**移动/跳跃**，**按不到 mod 键位**；桥侧**没有按键通道**。
- ⇒ 对"功能由按键切换"的模组，harness 连"把功能打开"都做不到 ⇒ 渲染/视觉类缺陷的根本证据无法产出。

**当时要求的 4 条**（现由 `0fde59a` 实现，逐条对照见 §1.1/§1.2）：① 按客户端键位（不硬编码 `L`）、
press/release/按住 N tick；② 属写操作 ⇒ 走唯一守卫编码点（默认关、token、单人/白名单主机、每次放行恰 1 行
`ALLOWED-MUTATION`、token 字面 0 次）；③ 收据三态 —— 按键是否被采纳不可自证时 `notClientVerifiable`，
**不许声称"灯已开"**；④ 验收 = **用 TacLight 按键后能拍到"有光斑"的画面**才算达成。

### 1.1 harness 侧怎么用（往文件中继 `<gameDir>/taclight-cmds.txt` 发一行即可）

| 命令 | 语义 |
|---|---|
| `!key <name> down` | 按下并保持（等价物理按住）；有 **60 s 硬上限**兜底自动抬起 |
| `!key <name> up` | 抬起 |
| `!key <name> <ms>` | 物理按一下（click + down），到点自动 up；`ms ∈ [1, 60000]`（超界报错，**不静默 clamp**） |
| `!key hotbar.N` | **纯选择键**，`N = 1..9`；⚠️ **见 §1.3 坑 1** |
| `!key list` | 可注入名字 + 各自消费路径 + 注入计数 |
| `!key clear` | 全部抬起（含 `releaseAll()` 清 clickCount）⇒ **每轮收尾必须调用**，防卡键 |

**20 个可注入名字**（= `!key list` 的**输出顺序**）：

- **vanilla / tick 路径（14）**：`use`、`attack`、`jump`、`sneak`、`sprint`，以及 `hotbar.1` … `hotbar.9`
- **TacLight / event 路径（6）**：`flashlight`、`gunlight`、`debug`、`diag`、`bench`、`snapshot`
  （= 物理键 **L / M / K / N / B / F9**），各自有一个**程序化等价命令**：`!light`、`!gun`、`!neon`、`!diag`、`!bench`、`!snap`

**为什么这条通道值得信**（不是推测，是字节码依据）：注入走 `mc.keyboardHandler.keyPress(...)` ——
与**真实按键回调调用的同一个方法**（首行只校验 window 句柄），内部 `set + click + fire InputEvent.Key`
⇒ **vanilla（tick 路径）与 TacLight（`consumeClick` 读 clickCount）同时覆盖**，避开了"只 `setDown` 会静默无效"的坑；
且**与窗口焦点无关**（我们的轮次窗口不聚焦）。

### 1.2 harness 侧怎么验收（可判定）

按键**是否被客户端采纳不可自证** ⇒ 默认立场是收据三态里的 `notClientVerifiable`，**不许写"灯已开"**。
可判定的做法是把"按键 + 旁证"钉成因果：

1. **取基线**：同一姿势下先 `!shot`（并用 `!diag` 记下 `flash=false` / `ssbo=0`）；
2. **发按键**：先 `!key hotbar.N` 选中手电筒，再 `!key flashlight 500`；
3. **旁证（缺一不可）**：`!light` 回执（`ignoring (not holding flashlight)` vs `true/false`）、`!diag` 的 `ssbo count` 变化、
   以及**截图里出现的光斑**；
4. **反向对照**：再发一次同一按键 ⇒ 光斑**消失**（切换类语义）。两条都成立才记达成；
5. **收尾**：`!key clear`，并确认 `!key list` 里没有遗留按下的名字。

**离线可跑的判据**：光斑的有无/大小用 `tools/analyze-regions.js` 在**同一区域**上比对（区域平均亮度 + `lit>=128`
像素数）。整图差会被极光/枪模/雪粒子主导，**不要用整图** —— 这是 2026-09-25 那一轮的教训。
**首个真机验收轮**：`docs/evidence/2026-09-27-keyinject/`（`PLAN.md` + `drive-keyinject.ps1`：r1 = 基线 / 负对照 /
hotbar 扫描 / 长按后不 clear 的异常路径；r2 = "灯开 → 光斑出现 → 再按 → 消失"）。

### 1.3 ⚠️ 两个已知坑（跑轮前必看，都会让整轮静默失效）

1. **裸 `!key hotbar.N` 在 `0fde59a`（当前 HEAD）上只回 `usage:`**：该版本**要求显式动作**，于是 9 个槽
   **全部静默失效**（`KeyInject.java` 自己记的 2026-09-26 task-14 缺陷原文："9 个槽全部只回 `usage:`,脚本静默失效"）。
   **"纯选择键缺省 50 ms 点按"的修法目前未提交**，只在 `taclight` 的工作树里（task-14）。
   ⇒ **跑 hotbar 扫描前，先用单步 `!key hotbar.1` 确认判据是否成立**，并核对所用 jar 是否含该修法
   （BACKLOG §2.27④：`build/libs` 里的 jar **可能是旧提交的**，拿它跑验收会得到假阴性）。
2. **`!key list` 的注入计数 `press=`/`release=` 曾经恒为 0**：旧实现记账用 `KeyMapping.getName()`
   （如 `key.taclight.flashlight_toggle`），而 `!key list` 用可注入名（`flashlight`）查 ⇒ 两侧名字永不相等。
   ⇒ 若所用 jar 较旧，**不要**把 `press=` 当判据，退回看 `down=` 与日志行（同上 task-14 修）。

### 1.4 仍未达成（诚实边界）

⇒ 在 `docs/evidence/2026-09-27-keyinject/` 产出**"光斑出现 + 光斑消失"两张可判定截图**之前，

## 2. ❌ 缺口 B：破坏 / 挖除动作（真人的左键）

**证据**：`world.place` **只能放置/替换**；"把雪层挖掉"**做不到**（雪层是可替换格，但没有任何 op 能移除方块）。任何"必须挖掘才能构造"的现场都做不了。

**要做的**
1. **新增破坏 op**（等价真人在准星处左键：开始破坏 → 进度 → 方块消失），**必须走真实交互路径**（与 `world.place` 的 P11 修正同一原则：**不得直接改世界**），否则服务端不认、事件不触发；
2. **守卫**：写操作，同 §1 第 2 条；
3. **收据**：`requested`（目标格/时间预算） vs `observedDelta`（读回该格变化）；破坏可能被服务端拒绝或部分完成 ⇒ **三态如实**，**不许 `ok:true` 就暗示"已破坏"**；
4. **验收**：用真实方块（如 `minecraft:snow` 层）做一次"破坏前后 `state.query` 读数变化 + `block_placed`/破坏事件"闭环。

**推论**：有了它，**"雪层挖掉前后对比"这类变量控制才成立**（当前只能靠"替换或换点对比"）。

## 3. ❌ 缺口 C：客户端命令通道（模组自己的调试开关）

**证据**：`!voxel on/off/status` 是 TacLight 的**客户端**命令；KubeJS 是**服务端**，`!` 命令到不了客户端 ⇒ **模组自带的 A/B 隔离开关用不上，只能人手工敲**。而"体素栅格 vs 屏幕空间 SSO"的分离，正是这个开关最容易做的。

**要做的（二选一或都做）**
- **C1 通用**：一个"执行客户端命令"的 op（**必须守卫 + 收据三态**，因为它是任意威力写操作）；
- **C2 契约化**：为 mod 提供**注册调试开关的接口**（mod 侧声明自己的开关名与取值），harness 侧只允许拨动**已声明**的开关——**比 C1 安全得多，推荐**。

**验收**：能通过桥侧把 TacLight 的 `!voxel` 在 on/off 之间拨动，并观察到**可判定的画面差异**。

## 4. ⚠️ 缺口 D："能截不能判"（能力边界，不是缺陷）

**证据**：`shot.capture` 收据原文 **`image content is NOT interpreted`** ⇒ **能产出可判定画面，不能自动判定**。⇒ 渲染类缺陷仍需**人眼**（本会话就是如此：三张图的视觉判定最后交给人）。

**要做的（可选，优先级中）**
- **D1 亮度/像素比对**：对同 pose 的两张截图做**可复现的差分**（如"亮斑像素占比""方格阵列的空间频率"），给出**数值 + 阈值**，把"阵列是否消失"变成**可自动判定**的量；
- **D2 明确标注**：在 `shot.capture` 与工具说明里**写死"不解释图像内容"**，避免调用方误以为它判过了（现在收据里有，工具描述里也应强化）。

## 5. ⚠️ 缺口 E：场景构造能力受限（能找、能放，不能造）

**证据**：`state.query` 能扫出地形直方图（本轮 `air x60 / smooth_stone x25 / black_concrete x15`），`world.place` 能构造非满方块现场（门已实测成功）——**但**：① 不能造**自然地形**（无雪、无生物群系）；② 不能挖（§2）；③ **没有"瞄准"控制**（准星朝向只能靠 `pose.set` 的 yaw/pitch 近似，没有"看向某坐标"的复合 op）。

**要做的**
1. **`look.at(x,y,z)` 复合 op**：把准星朝向给定坐标（含容差与失败原因），**这是"造一个可判定的观察"最常用的一步**；
2. **（可选）`walk.within`**：已在 `task-80` 立项（走到目标可达范围内，含预算/两档取消/`stuck`·`timeout` 等非故障终止）——**与本节同一族**；
3. **不做**"造雪/造群系"这类作弊式能力（`/setblock` 级放宽不允许）；**改为**：让调用方能**声明所需现场**，harness 报告"现场是否存在"（能找就找，找不到如实说"手段受限"）。

## 7. 记录纪律（沿用本仓库既有标准，新能力一律照此验收）

- **每条新能力必须有**：① 守卫定级（读/写）+ 审计行口径；② 收据三态；③ "**旧码必红**"实测（临时回退 ⇒ 变红 ⇒ **逐字节还原** ⇒ 重跑全绿）；④ 四护栏绿；⑤ `PROTOCOL`/`catalog`/agent 面向工具描述同步；
- **未验证的不写成已验证**；**做不到的记"手段受限 + 原因"**，**不为凑判据放宽**；
- **取产物必须用 `:forge:build`**（只跑护栏会留下未重混淆的次品，见 `task-77`）；
- 真机纪律：单实例 ≤150 s、一次一个、强制 `java=0`、报墙钟/峰值/内存。
